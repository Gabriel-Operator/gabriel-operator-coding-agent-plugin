# Reviewed community activity loop

Use this contract when the domain outcome is an actual family gathering or school workshop. Keep discovery, an editable proposal, a published plan, participation consent and a physical occurrence separate. Planning execution completion never establishes attendance.

The parent model owns `peopleMatchingConfig.proximity.activityLoop` and its matching `assets/community-activity-loop.json`: country configurations, source readiness, refresh/freshness, Signal thresholds, outcome policy and translated presentation. A saved geofence selects the country; language only changes presentation. Google Maps settings remain encrypted in Edit Persona / Publish App; no build-environment keys or portable secrets.

One pinned workflow skill package owns the flagship questions, branches, schemas, prompts, copy, fixtures and locales. Bind `landingPage.capabilityPreview.commandId` and the Chat App primary action to that same command. With `teamExecution: true`, the actual guided dispatcher stages join the canonical inspected executable definition and require the standard authenticated owner team confirmation. Include the package fingerprint; prompt or schema changes invalidate old confirmation. Hero, floating chat and signed-in command project the same server preview. Share editable input within the same actor, persona, mode and session; expire local resume hints, reject old-account responses and ignore retired-preview events. Do not duplicate a persona-specific English or colour dictionary in the platform.

Native `community-observation` is a registered **Read** Data Feed source operation. It derives actor, active profile, school, country and radius from the runner. Direct ordinary-caller activity-loop refresh can inspect cached readiness; it cannot acquire an external source outside a consuming playbook. Declare country-specific variants, exact domains, optional source-ID/credential-slot mappings and ontology dependencies. Only declared slots for the selected source, or the runner’s own already-bound optional connections, enter the existing Guardian authorization flow. Calendar access uses free/busy, never appointment titles. Public venue data does not independently prove age suitability or school approval. Missing ages, dates, coordinates, capacity and fees stay unresolved. External events remain external: a linked family gathering does not reserve tickets, provider capacity, payments or invitations.

Author disabled Signal presets on the normal automations data point using portable observation List references and declared action IDs. Runtime consent, enabled state, history, deduplication, cooldown and evidence stay private. Signals prepare proposals; they do not approve publication, join another family, book a provider or alter an existing commitment. Replacements need a new review and new participation choices; the original occurrence remains auditable. Different school/area evidence cannot be reused after a scope change.

Adult check-ins require actual participation, an ended occurrence and a current report revision. Two distinct adult-managed family profiles must report attendance and children playing together before a neighborhood meetup is confirmed. School completion also needs organizer delivery and intended-group evidence. These are attestations, not GPS surveillance or independent physical verification. Missing/conflicting reports remain unknown; corrections can withdraw earlier confirmation.

Bind ROI to `source: "activity_occurrence"`, a stable `ActivityOutcome` identity and a real calculator path. Capture ontology/calculator definitions while publishing. Only server-loaded, validated occurrence evidence creates these observations; generated rows and client booleans do not. Evaluation activities are quarantined from live discovery and realized ROI. Count distinct confirmed occurrences, family participations, outcome coverage and repeat connections with a full observation window. Time value needs an explicitly saved baseline, measured organizing/review effort, comparable known cost and matching currency. Preserve negative values and missing coverage; do not price friendships or children’s play. Provider usage, allocated credits and unknown external tool/Maps fees remain distinct.

Discover the installed schemas for `get_activity_loop_context`, `get_activity_outcomes`, `get_activity_impact`, `set_activity_check_in`, `configure_activity_signals`, `set_activity_baseline` and ordinary nearby activity tools. Workspace MCP uses `gabriel_*` with a page ID; persona-bound MCP uses `persona_*` with server-bound scope. Neither route may manufacture human playbook-team confirmation.

Validate package fixtures and all locales, portable child pins, feed/country variants, disabled Signal definitions and ROI/ontology mappings. Exercise cross-school/geofence denial, missing setup, source freshness, false model facts, changed approvals, capacity, idempotent publication, conflicting/corrected reports, account/surface switches, login cancellation, reload and light/dark mobile/desktop views. A passing mock suite is not a human team review or an independently verified meetup.

Candidate preparation must use the candidate's immutable ontology and feed definitions. Materialize feed schemas for review with `candidateRevision` and `isLatest: false`; do not deprecate live definitions or revoke their grants. The runtime rejects staged acquisition outside an isolated evaluation. Normal publication promotes the exact feed revision and clears the candidate marker. Author team review validates the authored ontology revision; ordinary execution keeps the published semantic pin. Do not solve the review/publication dependency by marking a candidate live or manufacturing team confirmation.
