# Persona ROI: values from committed evidence

Use this when authoring a signed-in ROI/Impact view or its public calculator. Request Gateway skill topic `persona-roi`; read `assets/chat-config.json`, the parent `assets/ontology.json`, `assets/chat-app.json`, the calculator model and actual List/workflow output schemas first.

## Placement and shared definitions

Add a standalone domain ROI/Impact sidebar destination using registered `outcome-metrics`, `outcome-baseline`, `outcome-check-in` and `outcome-observations` components backed by `source: outcomes` data points with the monitoring `profileId`. Match Kai by retaining canonical `agents` (or existing `grocery-agents`) hidden workspace metadata for the sidebar route. Never show ROI in Home/Coach’s tab strip; aliases do not change ownership. This destination also must not duplicate Playbooks, routines, Signals or milestones managers.

Author `publishedConfig.roiMonitoring` and a real `calculatorPath` into the same landing model used by the public calculator. Public defaults are assumptions, not observed returns. Place the optional planning baseline directly beneath the ROI title, before the metric cards. Use a slim themed collapsible, concise single-line field labels, full persona questions in styled help tooltips, and equal-height aligned inputs and save controls. Render it once through the shared ROI component, not again below the charts. Start collapsed and show the current time, people and hourly-value inputs on the right; expanding uses those same values. Distinguish unsaved drafts from an explicitly saved baseline. A runner may copy calculator inputs into an editable baseline, then explicitly save it for future outcomes. Never auto-accept evidence or write a baseline simply because someone viewed a landing page.

## Algorithm and units

1. Capture monitoring/calculator revisions and the resolved country/audience/language ontology **while the run is active**. Store the immutable semantic snapshot in runtime measurement storage, not Git. Reuse it on retries; historical runs without a captured contract are unvalued.
2. Read committed structured workflow output or authorized run-linked List records. A prose success statement, demo, sandbox purchase, preview or subscriber evaluation is not realized value. Each binding declares its enabled workflow resource key, acceptance boundary, required evidence and `ontology: {entityType, recordsPath, fields}` using JSON pointers. For List-backed pipeline output, `/__roiRecordId` exposes only the server-supplied row identity for projection; it is not a new List column.
3. Validate the projection against the captured ontology. `identityAttribute` names a projected stable key so retries and repeated data collection do not sell the same row twice. Iterate all committed rows. Correction chains supersede older evidence, preserve audit history and withdraw removed/invalid evidence. A produced lead is not automatically an accepted opportunity, sale, placement or payout.
4. `valuation: {currency: "EUR", timeMetricId: "approved_plans"}` monetizes the **paired, self-reported** effort for that one outcome metric. Monetary time value = `(baseline minutes − preparation minutes − review minutes) × runner hourly value / 60`. The runner must save an explicit hourly value and matching currency. Preserve negative results. Time capacity is not cash savings. Unmeasured/unmapped outcomes remain counts with missing-value/coverage disclosures.
5. Optional `amountRules` declares `id`, `metricId`, `label`, `baselineAttribute`, `actualAttribute`, `currencyAttribute` and `scale` (e.g. `0.01` for minor units). A rule values the difference of two nonnegative committed amounts **only at its configured accepted outcome boundary**, with matching currency. Map the real comparable baseline and actual amount onto ontology attributes; never use a budget ceiling, listing price, loan principal, property price or gross pipeline value as realized benefit. Avoid overlapping rules that value the same benefit twice.
6. Sum only eligible values. Keep typed evidence: observation, invocation, source receipt/row, entity type, ontology revision/fingerprint, measurement coverage and provenance. Missing values stay `null`, never silently zero. Owner aggregates must omit runner-private evidence identifiers.
7. Report tokens and net consumed/refunded credits for the **same runner, persona and period**, including failed work. Investment is not a token count. Include run-only reservation/settlement receipts only when that run is in the trusted runner/persona history; an explicit different persona attribution excludes the receipt. A receipt matching both run and persona still counts once. If recorded USD top-ups provide prices, allocate consumed persona credits at the historical weighted acquisition price known when consumed: `credits × sum(paid USD) / sum(purchased credits)`. This is a labeled acquisition-cost estimate, not cash spend or an exact FIFO lot claim. General account top-ups are funding, not a whole-persona expense; provider cost is a separate basis. Never add token/provider cost, allocated credit cost and top-up funding together. Unpriced costs remain unknown.
8. Net value = eligible monetary value − comparable investment. ROI% = `(value − investment) / investment × 100` only with known positive investment, complete disclosed coverage and matching currencies. Do not silently equate EUR and USD or invent an exchange rate. Show the value and resource efficiency when a financial ROI is not yet measurable.

For Paya, value attaches to human-approved online shopping plans in the private purchase ledger. AgentCard capture uses a pipeline-stage binding with `ledgerSource: purchase`, its authoritative approval/payment state and merchant evidence. Sandbox requests are excluded. An order/budget total is an expense or ceiling, not a return. Price savings require a committed comparable-price baseline; Paya's current ledger does not provide that baseline, so it must not claim price savings.

Other domains must define their real unit: reviewed introductions, a qualified lead, an accepted form/case pack, reviewed inventory, an accepted learning/course plan, a campaign deliverable or a scrap assessment. Use output/List fields actually produced by the workflow. Measure accepted data/action value through reported effort or a separately evidenced economic rule; do not assign an invented market price to every row.

## Validation and agent access

Run the normal Chat App/model/workspace checks plus `node scripts/validate-roi-monitoring.cjs assets/chat-config.json assets/ontology.json`. It checks monitoring, the actual calculator path, ontology mappings and monetary rule attributes. Validate every reachable context replacement; an invalid projection must not generate value. Exercise acceptance, retries, multiple rows, withdrawals, wrong currencies, unknown costs, negative time and runner isolation with fixtures.

Read runner ROI with `gabriel_get_persona_roi(pageId, from?, to?)` or `GET /api/gateway/pages/{pageId}/roi`. Gateway scope is `api:access`, `mcp:access`, `digital-twin:admin` or `digital-twin:app:read`, plus normal persona visibility/password checks. Persona-bound MCP uses `persona_get_roi` with `digital-twin:app:read` and no caller-supplied page/user identity. Reads are private, do not execute agents, mutate records, accept outcomes or change prices, and reject periods over one year.

Configuration stays under the normal Git candidate/evaluation/publication and revision-check flow. Runtime rows, prices paid, token events, customer identities and credentials never belong in portable definitions.

ROI/Impact is sidebar-only. Use canonical `agents` (existing Kai `grocery-agents`) metadata as the standalone target; never display an ROI tab beside Meet/Coach.
