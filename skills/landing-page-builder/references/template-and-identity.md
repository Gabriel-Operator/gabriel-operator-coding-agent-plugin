# Select a landing template and author its identity

Use `template-catalog.json` to select a registered named layout.
The generic `default` renderer remains available for an existing plain presentation.
Catalog names identify layout references, not the identity of the persona being built.

## Selection and complete JSON

1. Honor an explicit template ID or its catalog persona name. If the user asks you
   to choose, recommend the closest structure for the brief. State in the plan:
   **I will use <catalog name> (<variant>) for <new persona name>.**
2. Set `landingPage.design.variant` to the catalog `id` in the model. Naming a
   source persona in prose, or setting a `templateId` field, does not select a layout.
3. Read `landing-page-contract.json` and the selected `contentModel` contract. A
   non-null model names a required `landingPage.<contentModel>` object; populate
   its complete bounded copy, arrays and media. A null model uses the generic
   landing fields. Keep the renderer-owned composition and interactions.
4. Adapt visible copy, offers, audiences, character names, image descriptions and
   localized variants to the new persona. Preserve schema keys, navigation target
   IDs and existing resource keys; do not run a global string replacement on JSON.
   Do not copy another persona's runtime records, testimonials, customer identities,
   commands or credentials. Specialized public demos retain their registered
   command/workflow requirements; omit or disable an optional demo when those
   requirements are unavailable. A visual template does not grant its operations.

For `klok` (Paya), use the complete [copy model example](klok-template-example.json)
as the structural reference for `landingPage.klok`, including `schemaVersion: 1`,
brand, SEO, household/business editions, UI copy and visuals. Replace its reference
copy, contact/booking details, demonstrations and every media URL with the new
persona's actual content; the example is not seed/runtime data. In particular,
set `klok.visuals.portraitImage`, `characterImage`, `logoImage`, `bannerImage` and
all scenario image/alt-text arrays. Omitted slots can show Paya's fallback art.
The purchasing UI retains its supported buying command/journey contract; use the
new persona's registered compatible capability instead of inheriting source
authority or inventing another workflow. The Gateway response includes this
example so a remote agent does not guess its UI fields.

## Original character and image generation

A new branded landing build includes an original persona identity unless the user
supplies artwork or opts out. Keep initial page creation independent of image jobs,
but report pending required artwork before claiming the branded landing is complete.
Preserve an existing approved character when revising a persona.

Write a concise character brief: persona name and role, human/illustrated/mascot
direction, appearance, silhouette, clothing, palette, expression and recurring
visual details. Use a fictional character unless the user supplies their own
reference. Match the chosen template's visual treatment without copying its face,
distinctive mascot, logo, name or decorative art.

Prepare these roles using the author's connected image-generation tool:

| Role | Generation and acceptance |
| --- | --- |
| Portrait | Generate the original character first. Square crop; recognizable at small size; face clear of the edge; no embedded text or watermark. |
| Hero character | Use the portrait as an image reference. Preserve the face, outfit and style in a full/three-quarter-body composition. Request a transparent background when the layout uses a cutout; preserve room for the UI. |
| Brand logo | A separate original mark for this persona; readable in a compact header and on light/dark surfaces. The portrait remains the chat identity. |
| Supporting media | Generate the selected template's required feature, process, background, mobile-preview or scene illustrations, with the same palette and reference character where relevant. Preserve required aspect ratios and bounded array counts. |

Use this prompt structure, filled with the actual brief:

> Create an original <portrait / hero character / logo / scene> for <persona name>,
> an AI <role> serving <audience>. Visual direction: <selected template treatment>,
> with <palette, clothing, expression and distinctive details>. Composition:
> <aspect ratio, crop, pose and space for surrounding UI>. For a character variation,
> use the approved portrait as the identity reference. <Transparent background when
> required>. Do not include the source template's persona, brand, lettering or watermark.

Discover the available generation capability; do not invent a Gateway image
generation tool. `gabriel_upload_asset` hosts generated bytes and
`gabriel_save_asset` registers actual provider URLs; neither generates images.
Save generated images through these existing tools and retain real asset IDs and
returned URLs. Private asset-library manifests stay private; public page images
must be accessible through the supported public media path. Do not put base64,
local paths, credentials or expiring provider links into published JSON. If no
generator is connected, report the missing capability and pending roles. Do not
reuse the source character or claim a placeholder is generated artwork.

## Wire the same identity across the persona

| Asset | Model location |
| --- | --- |
| Portrait | `pageProfile.profilePicture` through the profile editor/Gateway profile operation; `landingPage.heroChat.avatarImageUrl` for the hero chat. The shared app/Coach consumes the persona profile. |
| Logo | `landingPage.header.brandMark: "image"` and `landingPage.header.logoImageUrl`. |
| Hero cutout | `landingPage.heroCharacterImage` where the selected renderer supports it. |
| Template media | The exact selected content-model slots. For example, Boli uses its own `mascotImage`, `avatarImage`, `logoImage` and Minecraft variations. Read that schema rather than assuming every layout reads the generic hero fields. |

Use the new persona name in profile, header, authored hero/chat copy, alt text,
footer and localized variants. A template's stable section IDs may still contain
its reference name and must remain unchanged. Keep portrait and logo roles distinct.
Persist brand palette and typography in `landingPage.design`; use the shared Chat
App sidebar treatment and semantic colors instead of adding arbitrary CSS or props.

## Save and verify

Mirror the landing definition into `publishedConfig.landingPage` using the existing
portable asset workflow. Run the maintained landing and Chat App validators and
workspace release checks against those exact saved files. Verify the accepted
template ID, actual rendered layout, newly hosted images, correct persona names,
mobile crops, transparency, anonymous image access and light/dark contrast. Check
the login transition into the same persona's signed-in app. Retain the shared
language selector, agent-install entry and command authorization boundaries.

Report the selected catalog name/ID and the created asset roles in the handoff,
followed by the returned canonical `/persona/<slug>` URL after successful publication.
