# Connector setup through MCP

Connect the coding agent to `/mcp/gateway` on the user's Gabriel origin with the same account-level Bearer API key used to create the app or game (`studio-apps:write` or `api:access`). Call `tools/list` first. The packaged `connector-app.cjs` accepts the gateway operation names in parentheses below as its HTTPS API fallback, with a JSON input file. Keep that file and tool results private. Never put the key or a provider credential in an app package, prompt, URL, or Git.

| What you do in Studio | What the coding agent calls |
|---|---|
| Pick a catalog connector or reuse a saved account | `gabriel_list_connector_apps` (`list`) and `gabriel_list_connector_connections` (`connections`). Match the intended account and provider; do not assume the first account is the right one. |
| Add a remote MCP endpoint, then click Connect | `gabriel_connect_connector_mcp` (`connect`) with `label` and `endpoint`, then `gabriel_authorize_connector_mcp` (`authorize`) with the returned `connectionId`. If it returns `authorization_required`, open its `authorizationUrl` for the user to grant access at the provider. An expired link can be regenerated on the same connection. |
| Load a managed account and choose actions | `gabriel_list_managed_connector_accounts` (`managed-accounts`) and `gabriel_list_managed_connector_actions` (`managed-tools`) with `appId` and optional saved `keyId`. Use `gabriel_authorize_managed_connector` (`managed-authorize`) only if the intended account needs a new provider sign-in. |
| Save the chosen managed account and its exact actions | `gabriel_connect_managed_connector` (`managed-connect`) with `appId`, `accountId`, `label`, optional `keyId`, and the reviewed `tools` array. Reuse a connection that already has the approved scope. Do not add tools to an existing grant silently. |
| Inspect the account; choose action inputs or view fields | `gabriel_inspect_connector_mcp` (`inspect`). Pin the returned tool fingerprints. For a needed private sample, use `gabriel_preview_connector_read` (`sample-read`) with `connectionId`, `tool`, `fingerprint`, `arguments`, and `confirmedRead: true`. This calls only a tool explicitly marked read-only and not destructive. Skip sampling for action-only connectors. |
| Validate actions and preview the installation | `gabriel_preview_connector_app` (`preview`) with `package: {manifest, files}` and the relevant connection IDs. For a public action-only connector use a generated UI, `entities: []` and `monitoring: []`. Map named runtime inputs in operation arguments with `$/values/<name>`. |
| Register a custom app/game and install it | `gabriel_register_connector_app` (`register`), then `gabriel_install_connector_app` (`install`) with `pageId`, `personaWorkspaceId`, `spaceId`, `appId`, `label`, and a stable `idempotencyKey`. Private apps use the registered `appRevision`; a public connector supplies its reviewed `manifest`. Omit `connectionId` for apps with no primary connector. No synchronization, monitoring, or execution starts. |
| Inspect the installed revision and save optional data bindings | `gabriel_list_connector_installations` (`installations`), `gabriel_get_connector_installation` (`data`) and `gabriel_configure_connector_installation` (`configure-setup`). Use the current `expectedRevision`; do not turn on synchronization, automatic rules, or spending during setup. |
| Finish playbook setup | `gabriel_get_connector_setup` (`connection-setup`), `gabriel_preview_connector_result_mapping` (`result-mapping-preview`) with sanitized fixtures, and `gabriel_bind_connector_requirement` (`bind-requirement`). Send the logical `requirementId`, `context`, `installationId`, exact action mappings, reviewed `sharedFields`, and `expectedRevision`. `context: "app"` also needs `appId` and owner authority. Recheck readiness before any run. |

Use the exact `pageId`, `personaWorkspaceId` and `spaceId` for all team operations. A Team Manager session can use its own `app_studio_*` equivalents for private app setup, direct OAuth (`app_studio_authorize_connector`), connector read samples, installations, and logical mappings. Managed project setup uses the account-level app key; a team-only session does not acquire that authority.

A workspace owner can set the playbook allowance on a visible connected app with `app_studio_set_app_allowance` in the Team Manager session. Read `app_studio_list_connectors` for the installation ID and current revision. Supply `expectedRevision` and `playbookAllowance` with `remainingCredits` and `remainingModelCalls`. Approve the exact request in Coach and repeat it with its `approvalId`. The allowance caps spending on that installation. The person who connected it retains control of its private source account. Result-field sharing is configured separately in the playbook requirement mapping.

Browser consent is the remaining provider interaction. The user signs in to the real provider and reviews the requested scope. The tool neither clicks consent nor accepts an authorization code, password, or raw access token from the agent. A Composio project key or provider API key that is not already saved belongs in account settings or the vault. Installation and requirement mapping do not replace the exact execution review for an email, booking, recording, or other external effect.

## Lane: Prospect to pilot

- **Gmail:** Canvas → Gmail → Inspect account and continue. Reuse the saved managed connection. Select exactly **Read an email conversation** (`GMAIL_FETCH_MESSAGE_BY_THREAD_ID`, `read`) and **Send an email** (`GMAIL_SEND_EMAIL`, `write`). Map `thread_id` to `$/values/threadId`, `recipient_email` to `$/values/to`, `subject` to `$/values/subject`, and `body` to `$/values/body`. Validate playbook actions, leave data bindings empty, preview and install as **Lane pilot Gmail · approved actions**. It becomes selectable under **Finish playbook setup**. A new-message send is not a thread reply. Leave the mailbox requirement incomplete until a separately reviewed, dedicated reply operation is available and the reply result/status mappings have been verified.
- **Notion:** Canvas → Notion → Connect Notion, using the official `https://mcp.notion.com/mcp` endpoint. The coding agent uses the direct MCP authorization steps above. Review the account and workspace in the provider; the workspace grant follows the signed-in account's page permissions. In local development, approve the callback only if it returns to the expected local Gabriel server. After callback success, inspect again and pin only the approved disposable destination and operations. Do not confuse OAuth with permission to write to the CRM or share an account with the team. Any shared destination mapping and List/page publisher use the owner's existing authority and explicit field allowlist.
- **Verification:** Inspect the saved account, installation, and requirement readiness separately. Record which steps actually completed. No test email, booking, capture, Notion write, paid run, or recurring automation is part of setup.
