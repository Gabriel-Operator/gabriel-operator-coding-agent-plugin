# Connector app builder

Create a private app using only this distributed pack and authenticated Gabriel tools. No Gabriel checkout, persona-author token or administrator role is needed. Public catalog apps stay platform-maintained; every custom package, connection, preview and installation belongs only to its creator. Only explicitly mapped team fields and task outputs become shared.

This skill is published at [Gabriel-Operator/connector-app-builder](https://github.com/Gabriel-Operator/connector-app-builder). Install it with `npx skills add Gabriel-Operator/connector-app-builder`.

Read [the package and scoped bridge contract](references/contract.md), [the workflow examples](references/workflows.md), and [the Studio-to-MCP connector setup steps](references/connector-setup.md). The machine-readable package schema is [connector-package.schema.json](references/connector-package.schema.json). Use the included scripts rather than inventing endpoints.

For a coding agent without the plugin, authenticated skill-topic discovery returns `authenticatedPackUrl`. Download that ZIP using the same account credential, extract it locally and run `npm install --ignore-scripts` inside `connector-app-builder` for the offline validator. The pack contains every referenced schema, helper and compiled styled-control asset. Initialize an app with `node scripts/connector-app.cjs init <app-directory>`, then author `app-config.json`, install the app's dependencies with `npm install --ignore-scripts` and run its build before packing.

## Apps and games

An app and a game are the same private package. Ask whether the person wants an app or a game, what it should show and do, and which connectors, Lists, saved state, and playbooks it may use. Then build, preview, register, and install the bundle. Claude Code and Codex are examples of coding assistants; any assistant connected to this team's MCP uses the same tools.

A package with no remote service sets `ui.kind` to `bundle`, leaves `entities`, `actions`, and `monitoring` empty, and uses a display `view` such as `content`. Omit `source.endpoint` and `source.toolkit`. Do not invent a connection id. Register and install omit `connectionId`. Named entries in `connectors` stay required when declared.

Set `state: true` when the page may save one JSON object, at most 256 KB, through `gabriel_app_state_read` and `gabriel_app_state_write`. Writes send `expectedRevision` and a `requestId`. A stale revision returns 409.

A List binding uses `source: "list"`. `gabriel_app_list_read` returns mapped columns, the record id, and the mapped-field revision for any direction. `gabriel_app_list_write` is allowed only when direction is `outbound` or `both`. An inbound binding is imported from the connector, so the page can read it and cannot overwrite it. Writes send only mapped fields and the current revision for an update, or a `requestId` for a new row.

`playbooks` holds at most 20 entries: `{ key, label, inputFields, maxCredits, maxModelCalls }`. Keys are unique. `inputFields` are unique and at most 50. `maxModelCalls` is 1–128. `maxCredits` is a positive finite number. These are the cap for one start. The owner sets the remaining credits and model calls under App → Customize → Assistant allowance before the page can start a run. Do not send `playbookAllowance` from the agent. The page calls `gabriel_app_playbook_start` with `playbookKey`, `input`, and `idempotencyKey`. Input keys must be a subset of that playbook's `inputFields`. `gabriel_app_playbook_status` reads a run only when its playbook is declared on this app.

The page stays sandboxed: `connect-src 'none'`, no iframes, no CDN, and no token. It loads state through the bridge. Do not put saved state or the allowance into the frame payload. Start from `assets/src/main.js` for a table, or `assets/src/canvas.js` for a canvas that reads and writes app state. Form fields use `gabriel-ui.js`.

## Apps and connectors

Studio → Apps → New app opens the private app authoring guide. Studio → Connectors → Add connector → My connectors saves a private MCP or REST connection without creating an interface. Reuse existing connections when building an app; do not turn every connection into another app. An app can require several connectors, and several apps or playbooks can use one connection within its grants.

With a team-scoped Team Manager connection, call `app_studio_app_builder_skill` and download its authenticatedPackUrl using that team key to get this complete pack. Then use `app_studio_connector_accounts`, `app_studio_inspect_connector`, `app_studio_preview_private_app`, `app_studio_register_private_app` and `app_studio_install_connector` instead of account gateway calls. Inspect the installed app with `app_studio_app_data`; prepare bindings or remove the installation using `app_studio_configure_app`. That tool cannot enable synchronization or automatic rules. These retain the signed-in member's identity and the current team's installation boundary. Never request an author's credential. Use the same package schema and bundled controls below.

## Services without a public connector

A persona's Featured tab can list a local service that has no public connection (a listed service, `provider: "directory"`; installing it answers 422 `CONNECTOR_APP_LISTED_ONLY`). When a team must actually work with that service, or with any service the persona's app plan names that has a remote HTTPS MCP but is not in the public catalog, save its endpoint in My connectors, signed in as the person who will use it. Build an app here only when a custom interface is wanted. It is never written into the persona definition, other members and subscribers do not inherit it, and each person who needs it builds their own. Check that the persona's `chatApp.studio.connectorApps.allowCustom` is not `false` first. A service needs a supported remote MCP or a documented HTTPS REST API; browser-only services remain unavailable. Do not wrap an unrelated tool. Adding a service to the public catalog or a market layer is a platform change described in the persona-builder skill's Studio apps contract (app plan, step 5).

## Authentication

Use the signed-in user's account-level API credential with `studio-apps:read` and `studio-apps:write` (or existing `api:access`). Keep it in `GABRIEL_API_TOKEN` and set `GABRIEL_BASE_URL` to the user's Gabriel HTTPS origin. Never request an admin credential, put tokens in a package, log tokens, or use another user's account. Workspace-bound credentials remain confined to their original workspace and cannot register account apps.

## Authoring workflow

1. Ask whether the person wants an app or a game, what it should display and do, and which connectors, Lists, saved state, and playbooks it may use. Identify required and optional services. For a new connection, ask for its remote HTTPS MCP or REST endpoint and intended operations. Local stdio must first be exposed through a supported remote gateway. Create an encrypted connection with `gabriel_connect_connector_mcp`; inspect with `gabriel_inspect_connector_mcp`. Existing connections are available through `gabriel_list_connector_connections`. REST uses `gabriel_connect_connector_rest` with explicitly declared operations; inspection returns normalized tool schemas without making a provider call. Authentication is kept separately in the connection. When a provider requires a key or bearer token, have the user save it in the vault with the provider’s documented header. Pass only the resulting connection reference to the agent. Do not put credentials in the MCP URL, REST query parameters, or packages.
2. Use `gabriel_authorize_connector_mcp` to inspect or return a fresh authorization URL. The user grants provider consent in the browser; inspect again afterward. Never ask the agent to collect a provider password or authorization code. Prefer official MCPs. For a managed catalog session, list the user's active accounts and available actions, then use `gabriel_connect_managed_connector` to pin one account and the exact reviewed action list, without shell, proxy or dynamic execution tools.
3. Save the discovery schemas and fingerprints. An MCP URL is not a data schema. Use tool descriptions, authorized read samples and sanitized fixtures to identify result arrays, stable identities, revisions, pagination and field meanings. Ask only about unresolved semantics. Do not infer write/monitoring support from the app's name.
4. Create `app-config.json`, sanitized `fixtures/*.json`, and either a bundled `mcp-app.html` with static assets, or a discovered provider `ui://` resource. Start from `assets/`. The included `gabriel-ui.js` bundles Gabriel's shared Input, Textarea, FormSelect, Switch, Checkbox, disclosure components and DOM field factories. Use these controls for labels, keyboard behavior, validation, disabled states and masked credentials. Never add ad hoc native feature controls. Provider tokens never enter the UI.
5. Declare additional app prerequisites in `connectors: [{key,label,purpose,required,endpoint?,toolkit?}]`. Assign the matching `connector` key to each operation (and provider UI when needed); omitted keys use `source`, the primary connector. Never embed connection IDs in the package. Installation supplies `connectionId` plus `connections: {key: userConnectionId}`; required missing, revoked, wrong-user and wrong-provider connections block use. Registering a package may precede additional account setup. Use declarative JSON Pointer mappings for reads/writes and background events. Fixed tool arguments select the permitted remote resources. Only declared dynamic values may change. Keep unsupported writes, deletion propagation and unavailable monitoring disabled. Uploaded JavaScript runs in the browser sandbox only; it cannot define a backend adapter.
6. `node scripts/connector-app.cjs pack <app-directory>` validates and creates `connector-package.json`. Install the starter's npm dependencies and build its UI first when using a bundle. Preview using `gabriel_preview_connector_app` or the helper. Check sanitized fixtures, field meanings, styling, keyboard interaction and scope rejection. A fixture preview is not evidence of a live provider integration.
7. Register with `gabriel_register_connector_app`, supplying the connection, package, `expectedRevision: 0` and a stable idempotency key. Updates pass the returned app ID and expected revision. Packages are immutable and installations remain pinned. An interrupted upload retries the same package and identity; never mint another identity to hide an uncertain result.
8. Install using `gabriel_install_connector_app` with the authorized page, workspace, team and connection IDs. In Studio → Apps → New app choose the registered revision, select all required connector accounts and remote resources, map List columns/assets/committed outputs, preview and separately activate synchronization. App → Customize → Integrations shows required accounts and supports reconnecting; connection changes pause synchronization and invalidate automatic-rule approval. Multiple resource installations are allowed. Packages and connections remain creator-only. The owner can explicitly share an installed bundled app through Customize → App access → Sharing: Owner only (default), Anyone signed in to Gabriel, or Public (no login). Shared launches delegate only the installation’s declared operations through its selected accounts and remaining assistant allowance. Package registration, installation and MCP authoring never implicitly change sharing. The owner explicitly chooses the access mode in the sharing controls; launch URLs never contain credentials. Changing operations, accounts, mapped data or the owner grant invalidates shared access until reapproved.
9. Prepare monitoring rules with the event, scope, conditions, target bot, prompt and explicit task/input mappings. Preview a sanitized sample. Writers prepare rules; the team owner reviews the mapped source, fields, target and limits before activating automatic runs. Do not claim that registration, installation or a coding agent grants automatic execution authority.

## Verification and recovery

For external UI hosting, keep agents, connectors, data and allowances on Gabriel. The owner can download the installed UI from Customize → Code and hosting, or include the original local source with `node scripts/connector-app.cjs export <app-directory> <deployment.json>`. The deployment JSON contains `backendUrl` (a stable Gabriel HTTPS origin), `installationId` and the installed `appRevision`; it contains no account credential. Read [hosting/README.md](hosting/README.md). The export includes Cloudflare Workers, Railway and Vercel configuration and a Dockerfile for Cloud Run or AWS. It requires current Public sharing, pins the app revision and exposes only the declared launch bridge. Changing sharing or the installed revision stops the exported bridge. Deploy under the user's chosen account, test a fresh browser and a real declared connector action, then verify and save the permanent URL in Code and hosting to update phone QR codes. Internal Gabriel hosting stays available. A frontend hosted over a temporary backend tunnel is still temporary. Do not claim a deployment succeeded from offline validation alone.

Check a second user cannot list or fetch the package, connection, preview or Studio installation. The standalone UI and its scoped launch bridge are available to visitors only under the owner’s current sharing setting. Verify anonymous denial for Owner only and Gabriel-only; verify another signed-in account for Gabriel-only; verify no-login access for Public; and return to Owner only to verify revocation on data, UI, resources and bridge calls. Visitor profiles and assistant-run status are isolated per visitor. Verify permitted writes, rejected resource substitutions, current membership and schema changes. Synchronization and monitoring run in background services with the browser closed. Initial import is a baseline, polling defaults to five minutes, and reactive events group for 60 seconds per rule/resource while preserving occurrences. Deletions and simultaneous edits require resolution. Do not blindly replay an uncertain provider write. Revoke or remove the connection/app to stop its work; a new private revision is adopted explicitly.

Report separately: offline validation, fixture tests, authenticated preview and actual live-provider checks. Identify missing provider grants or unsupported operations precisely.
